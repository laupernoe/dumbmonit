# Redis и Valkey

Само хранилище в памяти: память относительно `maxmemory`, отклонённые
подключения, линк репликации и отставание каждой реплики, отказавшие снимки
и записи append-only файла, и размер keyspace.

DumbMonit открывает одно соединение, отправляет `AUTH`, затем `INFO`, и
закрывает его. Учётная запись, которую он использует, может выполнять только
`INFO` и `PING` и ничего больше: она не может читать, писать или даже
перечислять ключ. Поддерживаются Redis 6 и новее, Valkey и форки, отвечающие
на `INFO` так же (KeyDB, Dragonfly).

Отказы, за которыми стоит следить, — тихие. При `maxmemory` Redis либо
вытесняет ключи без предупреждения, либо отклоняет каждую запись с `OOM
command not allowed`, в зависимости от `maxmemory-policy`; без `maxmemory`
он растёт, пока ядро его не убьёт. Отказавший снимок заставляет Redis
отклонять записи, пока включён `stop-writes-on-bgsave-error`, что
происходит по умолчанию. Реплика, чей линк с primary не работает, продолжает
отвечать на чтения, с устаревшими данными.

## Что отслеживается

Все метрики с префиксом `dumbmonit_redis_`. Суммарные значения — это
счётчики: графики и правила превращают их в скорости.

| Метрика | Что | Метки |
|---|---|---|
| `version_info` | значение 1 | `product` (`redis`, `valkey`), `version`, `mode` |
| `role_info` | значение 1 | `role`: `master` или `replica` |
| `memory_used_bytes`, `memory_rss_bytes`, `memory_peak_bytes`, `memory_fragmentation_ratio` | память, как её считает Redis, и как её считает система | |
| `memory_max_bytes`, `memory_used_percent` | `maxmemory` и доля использования; отсутствует, когда `maxmemory` равен 0 (без лимита) | |
| `maxmemory_policy_info` | значение 1 | `policy` |
| `connected_clients`, `blocked_clients`, `max_clients` | | |
| `rejected_connections_total` | подключения, отклонённые из-за достижения `maxclients` | |
| `evicted_keys_total`, `expired_keys_total` | ключи, вытесненные при `maxmemory`, истёкшие ключи | |
| `keyspace_hits_total`, `keyspace_misses_total` | поиски, нашедшие свой ключ, и те, что не нашли | |
| `commands_processed_total`, `connections_received_total`, `ops_per_second` | | |
| `error_replies_total`, `acl_denied_auth_total` | отправленные ответы с ошибкой, и отклонённые входы (подбор пароля виден здесь) | |
| `keys`, `keys_expiring` | ключи во всех базах данных, и те, у которых есть срок истечения; присутствует всегда, даже при нуле | |
| `db_keys` | ключи на базу данных | `db` |
| `rdb_last_save_ok` | 0, когда последний снимок (`BGSAVE`) завершился ошибкой | |
| `rdb_changes_since_last_save`, `rdb_last_save_timestamp_seconds` | | |
| `aof_enabled`, `aof_last_write_ok`, `aof_last_rewrite_ok` | append-only файл; два статуса — только когда он включён | |
| `loading` | 1, пока Redis загружает свой набор данных при запуске | |
| `connected_replicas` | реплики, подключённые к этому primary | |
| `replica_online`, `replica_lag_seconds`, `replica_lag_bytes` | с точки зрения primary, на реплику: в сети или нет, секунды с последнего подтверждения, байт отставания | `replica` (`ip:port`) |
| `master_link_up`, `master_last_io_seconds`, `master_link_down_seconds`, `master_sync_in_progress` | на реплике: её линк с primary | |
| `uptime_seconds`, `cluster_enabled` | | |

Применяемые [встроенные правила](../alerting/rules.md#databases-message-broker-and-security-engine):
«Память Redis близка к maxmemory», «Redis отказывает в подключениях», «Линк
репликации Redis не работает», «Реплика Redis отстаёт», «Снимок Redis не
удался», «Запись append-only файла Redis не удалась», плюс «Устройство
недоступно».

## Страница устройства

Панель над графиками читает то, что сохранила проверка; открытие страницы
никогда не запрашивает Redis. Она сообщает, что не так, в одном предложении
(репликация, память относительно `maxmemory` и политика, применяемая на
пределе, персистентность, отклонённые подключения), затем — ключи, память,
клиентов, команды в секунду, долю попаданий, ключи, вытесненные за последние
24 часа, и время работы, затем — ключи на базу данных и отставание каждой
реплики.

## Создание пользователя Redis, которому разрешён только INFO

1. На Redis 6 или новее, либо Valkey, создайте пользователя, которому разрешены только INFO и PING и ничего больше, без доступа к какому-либо ключу. В redis-cli, войдя пользователем, которому разрешено управлять ACL:

    ```
    ACL SETUSER dumbmonit on >a-long-password -@all +info +ping
    ```

2. Сделайте это постоянным: ACL SAVE, если сервер загружает своих пользователей из aclfile, иначе CONFIG REWRITE.

    ```
    ACL SAVE
    ```

3. На Redis 5 или старее, либо только с заданным requirepass, выберите ниже Password only. Этот пароль несёт все права: предпочитайте пользователя ACL, когда сервер его поддерживает.

4. В DumbMonit введите адрес сервера, например «cache.lan» или «cache.lan:6380». Если сервер принимает на этом порту только TLS (tls-port), отметьте TLS ниже.

5. DumbMonit отправляет AUTH, затем INFO. Он никогда не читает, не пишет и не перечисляет ключ.

!!! warning
    Redis не предупреждает перед maxmemory: на пределе он либо тихо вытесняет ключи, либо отклоняет каждую запись, в зависимости от maxmemory-policy. Без maxmemory он растёт, пока ядро его не убьёт. DumbMonit предупреждает выше 90% от maxmemory.

## Учётные данные

| Учётные данные | Поля |
|---|---|
| Пользователь ACL (рекомендуется) | Пользователь, созданный выше, и его пароль, отправляются как `AUTH user password`. |
| Только пароль | Значение `requirepass`, отправляется как `AUTH password`. |
| Без аутентификации | Для сервера вообще без пароля. |

Адрес: имя хоста или IP (`cache.lan`), `host:port`, или строка подключения
(`redis://cache.lan:6380`; всё после порта игнорируется, а учётные данные,
записанные в ней, никогда не используются). Опции: порт (6379), TLS
(выключено), проверка сертификата, и таймаут всей проверки (10 с). При
включённом TLS сертификат проверяется по публичным центрам сертификации,
встроенным в DumbMonit; для приватного центра сертификации отметьте Accept an
unverifiable certificate.

В развёртывании Redis Sentinel или Cluster добавьте каждый сервер, который
хотите наблюдать: каждый сообщает о своей памяти, клиентах и
персистентности, а primary сообщает о своих репликах. Сам Sentinel не
покрывается.
