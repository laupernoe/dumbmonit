# GitLab (self-managed)

Обслуживает ли самостоятельно размещённый инстанс GitLab, и успевают ли
части, которые тихо несут на себе всё остальное: очереди Sidekiq, раннеры
CI/CD, миграции базы данных, оставшиеся после обновления, и — для GitLab
Enterprise Edition — лицензия.

DumbMonit читает `/api/v4/version` с **персональным токеном доступа** —
единственным вызовом, который обязан пройти: это доказательство, что GitLab
отвечает и что токен действителен. Всё остальное — Sidekiq, раннеры,
миграции, статистика инстанса, настройки регистрации и двухфакторной
аутентификации, лицензия, и проверка готовности в подробностях — читается из
конечных точек, которые GitLab резервирует для учётных записей
администратора, и пропускается без провала проверки, когда токен принадлежит
обычной учётной записи.

Отказ, за которым здесь стоит следить: **Sidekiq начинает отставать**. GitLab
продолжает отдавать страницы, пока очередь фоновых задач растёт, и ничего на
странице не говорит об этом, пока уведомление, вебхук или обновление
конвейера CI не задержится на минуты или часы.

## Что отслеживается

Все метрики с префиксом `dumbmonit_gitlab_`.

| Метрика | Что | Метки |
|---|---|---|
| `version_info` | значение 1 | `version`, `revision` |
| `readiness_check` | 1, когда компонент готовности (база данных, кэш, очереди, общее состояние, Gitaly) не в статусе `ok` | `check` |
| `sidekiq_queue_backlog`, `sidekiq_queue_latency_seconds` | ожидающие задачи и их возраст, на очередь Sidekiq | `queue` |
| `runners_total`, `runners_online`, `runners_offline` | раннеры CI/CD, известные инстансу | |
| `runner_offline` | значение 1 на каждый раннер не в сети (не более 32) | `runner` |
| `migrations_pending` | оставшиеся к применению миграции базы данных | |
| `migration_pending` | значение 1 на каждую ожидающую миграцию (не более 32) | `migration` |
| `projects`, `users`, `groups`, `forks`, `issues`, `merge_requests` | счётчики по всему инстансу | |
| `signup_enabled` | 1, пока публичная регистрация открыта | |
| `two_factor_required` | 1, пока каждый пользователь обязан настроить двухфакторную аутентификацию | |
| `license_info` | значение 1 (только Enterprise Edition) | `plan` |
| `license_expired`, `license_expiry_seconds` | истекла ли лицензия, и сколько времени осталось | |
| `pipelines_failed_recent`, `pipelines_pending` | отказавшие конвейеры в окне просмотра, и конвейеры ожидающие или выполняющиеся сейчас — только для проектов, перечисленных в опции «Projects watched for CI health» | `project` |
| `scrape_errors` | вызовы, доступные только администратору, завершившиеся ошибкой при последней проверке (0, если вызовы с обычным токеном даже не предпринимались) | |

Применяемые [встроенные правила](../alerting/rules.md#self-hosted-forges):
«Все раннеры GitLab не в сети», «Высокая загрузка Sidekiq GitLab», «Ожидают
миграции GitLab», «Истекает лицензия GitLab», плюс «Устройство недоступно».
Оценка безопасности проверяет настройки двухфакторной аутентификации и
регистрации, а также ожидающие миграции: см.
[Обновления от вендора и другие проверки](../using/security-score.md).

## Что не отслеживается

Собственный REST API GitLab не имеет конечной точки, которая говорит «доступен
более новый релиз GitLab»: в отличие от Nextcloud или Paperless-ngx, нет
самоотчитывающегося флага обновления для чтения, поэтому DumbMonit его не
заявляет. Сравнивайте версию выше со
[страницей релизов](https://about.gitlab.com/releases/) GitLab вручную, либо
следите за собственным уведомлением о проверке обновлений GitLab в области
администрирования.

Здоровье конвейеров CI читается только для перечисленных вами проектов: API
GitLab не имеет конечной точки «все отказавшие конвейеры» для всего инстанса,
только для отдельного проекта.

## Страница устройства

Панель над графиками читает то, что сохранила проверка; открытие страницы
никогда не обращается к GitLab. Сначала она сообщает, что не так (отказавший
компонент готовности, все раннеры не в сети, большая очередь Sidekiq), затем
— версию, затем — счётчики инстанса и настройки, прочитанные из API
администрирования.

## Создание персонального токена доступа на учётной записи администратора

1. Создайте персональный токен доступа на учётной записи администратора: avatar → Edit profile → Access tokens → Add new token. Назовите его так, установите срок действия, который вам удобно продлевать, и отметьте только область read_api: она читает весь API и ничего не записывает.

    ```
    dumbmonit
    ```

2. Очереди Sidekiq, раннеры CI, ожидающие миграции, статистика инстанса, настройки регистрации и двухфакторной аутентификации и лицензия — каждое читается из конечной точки, доступной только администратору: у GitLab нет для них более тонкой делегации. Токен обычной учётной записи всё равно работает; тогда читается только версия, а остальное пропускается без провала проверки.

3. В DumbMonit введите адрес, с которым вы открываете GitLab, например «gitlab.example.com» (HTTPS на 443) или «https://git.example.com» за обратным прокси, и вставьте токен.

4. Чтобы также наблюдать за конвейерами CI, перечислите числовые ID проектов (показаны на странице обзора каждого проекта, под его именем) в опции «Projects watched for CI health», через запятую.

!!! warning
    Персональный токен доступа на учётной записи администратора может читать всё, что может читать сама учётная запись, даже с областью read_api: у GitLab нет роли администратора только для чтения. Выделите для этого учётную запись бота, а не используйте свою собственную, и отозвите токен, если он когда-нибудь утечёт.

Проверка токена вручную, с хоста DumbMonit:

```
curl --header 'PRIVATE-TOKEN: YOUR-TOKEN' 'https://gitlab.example.com/api/v4/version'
```

## Учётные данные

| Учётные данные | Поля |
|---|---|
| Персональный токен доступа | Отправляется как заголовок `PRIVATE-TOKEN`. |

Адрес: имя хоста (`gitlab.example.com`) или `host:port`. Опции: протокол (по
умолчанию HTTPS), порт (443), проверка сертификата, таймаут запроса (15 с),
проекты, наблюдаемые для здоровья CI (по умолчанию нет) и окно просмотра
отказавших конвейеров (24 ч).

Проверено на GitLab Enterprise Edition 17.5 (по официальной документации
API).
