# Мониторинг удалённой площадки

Один DumbMonit, несколько сетей. **Релейный агент (relay agent)**,
установленный на удалённой площадке, выполняет от имени сервера опросы
назначенных ему мониторов и передаёт результаты по тому же исходящему
соединению, которое уже использует для отправки собственных метрик. Ничего не
нужно открывать на удалённой площадке, не нужен VPN и второй экземпляр, на
который надо смотреть.

```
 head office                              remote site (NAT, firewall)
 ┌──────────────────┐   HTTPS, outbound   ┌──────────────────────────────┐
 │ DumbMonit server │◀────────────────────│ relay agent                  │
 │  scheduler       │  probes to run  ──▶ │  runs SNMP / Proxmox / HTTP… │──▶ switch, NAS,
 │  alerting, UI    │◀── samples, verdict │  pushes its own metrics too  │    hypervisor…
 └──────────────────┘                     └──────────────────────────────┘
```

## 1. Опубликуйте сервер по HTTPS

Релей получает свои задания от сервера: сервер должен быть доступен с
удалённой площадки, как правило, по адресу `https://monitor.example.org` за
обратным прокси. По этому каналу передаются две вещи:

- **токен регистрации** (`dmon_…`) в заголовке `Authorization` каждого запроса
  — как для любого агента;
- **учётные данные мониторов**, которые опрашивает релей (сообщество SNMP,
  токен API Proxmox…), в расшифрованном виде, внутри каждого задания на опрос.

По обычному HTTP через интернет обе вещи можно было бы прочитать по пути:
поставьте сервер за HTTPS, прежде чем что-либо ретранслировать за пределы
собственной сети. В локальной сети или VPN HTTP допустим, и токен остаётся
единственным секретом в передаче, пока вы не назначите релею мониторы.
Учётные данные никогда не записываются на диск ни с одной из сторон: задание
на опрос живёт в памяти сервера, пока релей не сообщит о нём, а агент ничего не
хранит между двумя опросами.

Обратный прокси должен пересылать `/api/agent/relay` так же, как
`/api/ingest`, допускать тела запросов до 16 МБ (нагруженный гипервизор
сообщает тысячи замеров) и держать простаивающие соединения открытыми не менее
60 секунд: сервер удерживает запрос релея до 25 секунд в ожидании работы
(long polling).

## 2. Создайте токен регистрации

**Settings → Agents → New token** либо добавьте монитор типа *agent*.
Скопируйте значение `dmon_…`: оно показывается один раз.

## 3. Запустите релей на удалённой площадке

Любая машина на удалённой площадке с Docker, используя `docker-compose.agent.yml`
из репозитория:

```sh
DUMBMONIT_AGENT_URL=https://monitor.example.org \
DUMBMONIT_AGENT_TOKEN=dmon_… \
DUMBMONIT_AGENT_HOSTNAME=relay-lyon \
DUMBMONIT_AGENT_RELAY=true \
DUMBMONIT_AGENT_SITE="Lyon office" \
docker compose -f docker-compose.agent.yml up -d
```

Либо обычный агент, установленный однострочным установщиком, с двумя
дополнительными ключами в `/etc/dumbmonit/agent.yaml`:

```yaml
relay: true
site: Lyon office
```

Машина появляется в DumbMonit в течение нескольких секунд как обычный
монитор-агент, и на её странице написано *Relay · site Lyon office · relays
0 devices*. В журнале агента появляется `relay mode enabled: waiting for probes
from the server`, как только принят его первый пакет.

!!! note "До чего должен дотягиваться релей"
    Релей опрашивает мониторы из своей сети: ему нужен тот же доступ, который
    понадобился бы серверу, окажись он там, — UDP 161 для SNMP, 8006 для
    Proxmox, 5001 для DSM и так далее. Для мониторов **ping** контейнеру нужен sysctl
    `net.ipv4.ping_group_range` (уже задан в файле compose, см. [Ping ICMP без capability](docker.md#icmp-ping-without-a-capability)). Для мониторов в VLAN или
    link-local сети, а также для целей `localhost` используйте
    `network_mode: host`.

## 4. Назначьте мониторы релею

Добавьте удалённые мониторы как обычно — коммутатор SNMP, узел Proxmox,
проверка HTTP — с их адресом **так, как он виден с удалённой площадки**
(`192.168.10.1`, `https://pve.lan:8006`). В форме монитора, в разделе *More
options*, выберите в поле **Reached through** релейный агент вместо *Direct*.
Существующие мониторы переключаются так же; возврат к *Direct* снова
заставляет сервер опрашивать их самому.

С этого момента:

- сервер ставит в очередь опрос монитора на каждом интервале; релей забирает
  его за миллисекунды (он ждёт работы на сервере), запускает коллектор и
  сообщает результат;
- **Probe now** и определение профиля на странице монитора тоже идут через
  релей;
- *last probe* и ошибка монитора следуют вердикту релея. Если релей не
  забрал опрос вовремя, монитор показывает *Timed out: relay agent … did not
  pick up the probe* — проверьте, что агент запущен с `relay: true`;
- на странице агента показано *Relay for N devices*, а `GET /api/relays`
  перечисляет релеи с их площадкой и числом мониторов.

## Оповещения, когда релей недоступен

Релей, который замолчал, уносит с собой свои мониторы: их опросы
прекращаются, и все они разом стали бы *unreachable*. Релей рассматривается как
**родитель** каждого опрашиваемого им монитора (в дополнение к родителю,
которого вы могли задать): когда сам релей *unreachable*, оповещения его
мониторов показываются как `suppressed` с `suppressed_by` = релей, и уходит
только одно уведомление — о релее. Явно заданный вами родитель сохраняет свою
роль и побеждает, если недоступны оба.

## Ограничения

- Один релей на монитор. Монитор, опрашиваемый релеем, не опрашивается
  также сервером.
- Сами мониторы-агенты ретранслировать нельзя: они отправляют собственные
  метрики.
- Релей выполняет не более 8 опросов одновременно; опрос ограничен тайм-аутом
  опроса сервера (`DUMBMONIT_PROBE_TIMEOUT_SECS`) и не более 120 с на агенте.
- Релейному агенту нужны встроенные коллекторы: агенты старше этой функции
  игнорируют `relay: true`, и сервер сообщает об их опросах как о превысивших
  время ожидания. Переустановите с текущим бинарным файлом или образом.
