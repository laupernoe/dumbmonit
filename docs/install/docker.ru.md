# Установка с помощью Docker {#install-with-docker}

DumbMonit работает как один контейнер: сервер `dumbmonit` (сбор данных, API,
оповещения, веб-интерфейс) запускает собственную VictoriaMetrics для хранения временных рядов; её
бинарный файл поставляется в образе. Конфигурация и состояние хранятся во встроенной базе данных
SQLite. Один том, `/data`, содержит базу данных, секрет экземпляра и
временные ряды.

!!! note "Альфа-образ"
    `ghcr.io/laupernoe/dumbmonit:latest` — последняя помеченная альфа-сборка (amd64;
    образы arm64 пока приостановлены); `:edge` следует за последним коммитом в `main`. Чтобы запустить из исходников,
    `docker compose up -d --build` собирает тот же образ локально (около десяти
    минут в первый раз; нужен только Docker).

## Требования {#prerequisites}

- Docker Engine с плагином Compose (команда `docker compose version` работает).
- Машина, которая может обращаться к отслеживаемым устройствам. Достижимость самой машины
  с этих устройств не требуется, кроме [агентов](../devices/agent.md), которые отправляют
  свои измерения на сервер по HTTP.
- Свободный порт `8080` на хосте или другой порт на ваш выбор (см. ниже).

## Файл Compose {#the-compose-file}

Это `docker-compose.yml` из репозитория; сохраните его в отдельном
каталоге:

```yaml
# Один контейнер: сервер DumbMonit запускает собственную VictoriaMetrics (встроенную в
# образ) и хранит всё в одном томе. Чтобы использовать вместо неё внешнюю
# VictoriaMetrics, задайте DUMBMONIT_VM_URL — встроенная тогда не запускается.
name: dumbmonit

services:
  dumbmonit:
    # `docker compose up -d` загружает опубликованный образ (последний релиз; используйте
    # `:edge` для последнего коммита в main). Чтобы вместо этого собрать образ из этой копии,
    # выполните `docker compose up -d --build`: результат получит то же имя
    # и будет использоваться в дальнейшем.
    image: ghcr.io/laupernoe/dumbmonit:latest
    build: .
    ports:
      # Порт хоста настраивается: 8080 — оживлённый порт на машине
      # домашней лаборатории. `DUMBMONIT_PORT=8099 docker compose up -d` меняет его.
      - "${DUMBMONIT_PORT:-8080}:8080"
    volumes:
      # База данных SQLite, секрет экземпляра и временные ряды (/data/vm).
      #
      # Сервер работает от пользователя 65532 (не root). Именованный том, созданный
      # Docker, наследует этого владельца из образа: делать ничего не нужно. Привязанный каталог
      # (`./data:/data`) или том, созданный до этого изменения, нужно один раз передать:
      #   docker run --rm -v dumbmonit-data:/data alpine chown -R 65532:65532 /data
      # или, чтобы оставить файлы как есть, запустите контейнер от их владельца
      # с `user: "1000:1000"` (подойдёт любой uid: в образе нет /etc/passwd).
      - dumbmonit-data:/data
    environment:
      # Раскомментируйте, чтобы задать секрет самостоятельно, а не позволять DumbMonit
      # создать его в /data/secret.key. Он шифрует учётные данные устройств: потеряв
      # его, придётся заново вводить каждую из них.
      # DUMBMONIT_SECRET: replace-me-with-32-random-characters
      # Потерян пароль: `DUMBMONIT_RESET_PASSWORD=1 docker compose up -d` сбрасывает
      # пароль при запуске, и UI запросит новый; затем запустите снова
      # без этой переменной.
      DUMBMONIT_RESET_PASSWORD: ${DUMBMONIT_RESET_PASSWORD:-}
      # Встроенная VictoriaMetrics: срок хранения (месяцы или, например, 30d / 2y) и
      # бюджет памяти её кэшей. Домашней лаборатории из нескольких десятков устройств хватает
      # 256 МБ; увеличьте его, когда мониторите сотни хостов.
      DUMBMONIT_VM_RETENTION: ${DUMBMONIT_VM_RETENTION:-12}
      DUMBMONIT_VM_MEMORY: ${DUMBMONIT_VM_MEMORY:-256MB}
      # Внешняя VictoriaMetrics вместо встроенной:
      # DUMBMONIT_VM_URL: http://victoriametrics:8428
    # Минимум привилегий: никаких capabilities, без повышения привилегий, а
    # файловая система образа доступна только для чтения — /data (том) и /tmp (tmpfs) —
    # единственные места для записи. Мониторам ICMP «ping» capability тоже не нужна: sysctl
    # ниже позволяет (непривилегированному) серверу открывать сокеты ICMP echo внутри
    # собственного сетевого пространства имён контейнера. Удалите его, если ping не используется.
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    read_only: true
    tmpfs:
      - /tmp
    sysctls:
      net.ipv4.ping_group_range: "0 2147483647"
    # Сервер сам останавливает VictoriaMetrics: оставьте ему на это время.
    stop_grace_period: 30s
    restart: unless-stopped

volumes:
  dumbmonit-data:
    # Фиксированное имя, не зависящее от имени проекта compose: том — это то, что
    # вы резервируете и что должно найтись после обновления.
    name: dumbmonit-data
```

Затем запустите:

```bash
docker compose up -d
```

!!! tip "Сборка образа самостоятельно"
    `docker compose up -d` загружает опубликованный образ и игнорирует `build: .`.
    Из клона репозитория `docker compose up -d --build` вместо этого собирает
    тот же образ локально (около десяти минут при холодном кэше; тулчейн Rust или Node
    на хосте не нужен). Используйте это, чтобы запускать из исходников или из
    ветки.

## Встроенная VictoriaMetrics {#embedded-victoriametrics}

Образ содержит бинарный файл VictoriaMetrics (`/victoria-metrics-prod`, из
`victoriametrics/victoria-metrics:v1.152.0`). Если `DUMBMONIT_VM_URL` не
задана, сервер запускает его как дочерний процесс, слушающий `127.0.0.1:8428`,
хранит ряды в `/data/vm`, перенаправляет его строки журнала в собственный журнал,
перезапускает с нарастающей задержкой, если он падает, и останавливает при завершении работы. Ничего
не публикуется: порт остаётся внутри контейнера.

Стоит знать две переменные: `DUMBMONIT_VM_RETENTION` (по умолчанию `12` месяцев;
подойдут и `30d`, и `2y`) и `DUMBMONIT_VM_MEMORY` (`256MB`, бюджет
её кэшей; увеличьте для сотен хостов). Остальное — в
[справочнике по конфигурации](../reference/configuration.md#embedded-victoriametrics).

Чтобы использовать уже работающую у вас VictoriaMetrics, задайте в `DUMBMONIT_VM_URL` её
адрес (`http://host:8428`): встроенная тогда не запускается, а
`/data/vm` остаётся пустым.

## Первый запуск {#first-start}

Откройте `http://<your-host>:8080`. Новый экземпляр показывает экран `/setup`,
где вы создаёте первую учётную запись администратора (пароль не короче 12
символов).

Сначала экран запрашивает **код настройки**. Пока администратора нет,
сервер при запуске выводит в журнал одноразовый код:

```sh
docker compose logs dumbmonit | grep -A1 "setup code"
```

```
  First-run setup code: K7XQ4-M9PRT
```

Он подтверждает, что создающий учётную запись администратора управляет сервером, поэтому
кто-то другой в сети не сможет занять свежий экземпляр первым. Код хранится
только в памяти, меняется при каждом перезапуске, пока нет администратора, а неверные
попытки ограничиваются по частоте. Для автоматизированного развёртывания задайте
`DUMBMONIT_SETUP_CODE`, чтобы выбрать код самостоятельно.

![Экран входа](../assets/screenshots/login-light.png){ loading=lazy }

Затем добавьте первое устройство: см. [Добавьте первое устройство](first-device.md).

## Переменные окружения {#environment-variables}

Всё настраивается через переменные окружения; ни одна не обязательна.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `DUMBMONIT_BIND` | `0.0.0.0:8080` | Адрес прослушивания внутри контейнера. |
| `DUMBMONIT_DATA_DIR` | `/data` | База данных SQLite (`dumbmonit.db`), секрет экземпляра (`secret.key`) и данные встроенной VictoriaMetrics (`vm/`). |
| `DUMBMONIT_VM_URL` | *(не задана)* | URL внешней VictoriaMetrics. Если задан, встроенная не запускается. |
| `DUMBMONIT_VM_RETENTION` | `12` | Срок хранения во встроенной VictoriaMetrics: месяцы или `30d`, `2y`. |
| `DUMBMONIT_VM_MEMORY` | `256MB` | Бюджет памяти кэшей встроенной VictoriaMetrics. |
| `DUMBMONIT_VM_LISTEN` | `127.0.0.1:8428` | Адрес прослушивания встроенной VictoriaMetrics внутри контейнера. |
| `DUMBMONIT_SECRET` | *(создаётся)* | Секрет экземпляра, шифрующий учётные данные устройств и токены. |
| `DUMBMONIT_MAX_CONCURRENT_PROBES` | `64` | Число одновременных проверок, всех сборщиков вместе. |
| `DUMBMONIT_PROBE_TIMEOUT_SECS` | `10` | Максимальная длительность одной проверки. |
| `DUMBMONIT_FLUSH_INTERVAL_SECS` | `5` | Период записи в VictoriaMetrics. |
| `DUMBMONIT_LOG` | `info` | Фильтр журнала (синтаксис `tracing`, например `debug`, `dumbmonit=trace`). |
| `DUMBMONIT_AGENT_DIR` | `/agents` | Бинарные файлы агентов, раздаваемые по адресу `/download/…`. |
| `DUMBMONIT_RESET_PASSWORD` | *(пусто)* | Задайте `1`, чтобы при запуске сбросить пароль и все сеансы. |
| `DUMBMONIT_SETUP_CODE` | *(создаётся)* | Код настройки, запрашиваемый `/setup`, пока нет администратора. Если не задан, при каждом запуске в журнал выводится случайный. |
| `DUMBMONIT_COOKIE_SECURE` | *(выкл.)* | Задайте `1` за обратным прокси с TLS, чтобы пометить cookie сеанса как `Secure`. |
| `DUMBMONIT_ALERT_INTERVAL_SECS` | `30` | Период проверки оповещений (не меньше 10). |
| `DUMBMONIT_ALERT_HISTORY_DAYS` | 90 дней | Срок хранения истории оповещений. Об оговорке касательно её единицы измерения см. [справочник по конфигурации](../reference/configuration.md). |
| `DUMBMONIT_BACKUP_ENABLED` | вкл. | Плановые локальные резервные копии базы данных в `/data/backups/`. Настраиваются через `DUMBMONIT_BACKUP_DIR`, `_INTERVAL_HOURS` (24) и `_KEEP` (7); см. [Резервное копирование и восстановление](backup.md). |

Полный список с подробностями — в [справочнике по конфигурации](../reference/configuration.md).
Имена `EZYMONIT_*` из времён до переименования по-прежнему читаются как запасной вариант; см.
[Обновление](#upgrading).

## Резервная копия секретного ключа {#back-up-the-secret-key}

Сообщества SNMP, пароли и токены API шифруются с помощью AES-256-GCM ключом,
производным от секрета экземпляра. При первом запуске DumbMonit создаёт этот
секрет в `/data/secret.key` (внутри тома `dumbmonit-data`).

!!! danger "Резервируйте `secret.key` вместе с базой данных"
    Без него учётные данные устройств невосстановимы: база данных, восстановленная
    отдельно, даёт экземпляр, который ни с чем не может связаться. Сервер обнаруживает
    отсутствующий или изменённый ключ при запуске и отказывается продолжать с явным
    сообщением, вместо того чтобы молча сбоить при каждой проверке. Плановые резервные копии
    копируют его за вас — см. [Резервное копирование и восстановление](backup.md).

Если вы предпочитаете управлять секретом сами, задайте `DUMBMONIT_SECRET` в файле Compose
(32 случайных символа или больше). Храните его в менеджере паролей.

## Обновление {#upgrading}

```bash
docker compose pull
docker compose up -d
```

Миграции базы данных выполняются при запуске. Данные VictoriaMetrics не затрагиваются.

!!! tip "Сначала сделайте резервную копию"
    **Settings → Backup → Back up now** за несколько секунд записывает согласованную копию базы данных
    и `secret.key` в `/data/backups/`, и именно из неё вы
    восстанавливаетесь, если обновление пойдёт не так. См.
    [Резервное копирование и восстановление](backup.md).

### С версии 0.1.0-alpha.1 {#from-010-alpha1}

Начиная с 0.1.0-alpha.2 контейнер работает от пользователя 65532 вместо root. Том,
созданный в alpha.1, по-прежнему принадлежит root, и сервер отказывается
запускаться (`/data is not writable by the server`). Один раз передайте том новому владельцу:

```bash
docker compose down
docker run --rm -v dumbmonit-data:/data alpine chown -R 65532:65532 /data
docker compose up -d
```

Или оставьте файлы как есть и запустите контейнер от их владельца, указав
`user: "0:0"` (или uid привязанного каталога) в сервисе в
`docker-compose.yml`.

### С EzyMonit и с конфигурации из двух контейнеров {#from-ezymonit-and-from-the-two-container-setup}

До сентября 2026 года DumbMonit назывался EzyMonit и работал в двух контейнерах:
сервер и отдельный сервис `victoriametrics`. Для обновления данные
старого проекта нужно один раз перенести в новый том. Старый проект назывался
`ezymonit` (его тома — `ezymonit_ezymonit-data` и `ezymonit_vm-data`;
убедиться можно командой `docker volume ls`). Из старого каталога:

```bash
docker compose down
```

Затем, с новым `docker-compose.yml`:

```bash
docker volume create dumbmonit-data
docker run --rm -v ezymonit_ezymonit-data:/from -v dumbmonit-data:/to alpine cp -a /from/. /to/
docker run --rm -v ezymonit_vm-data:/from -v dumbmonit-data:/to alpine sh -c 'mkdir -p /to/vm && cp -a /from/. /to/vm/'
docker compose up -d
```

Каталог данных старой VictoriaMetrics имеет ту же структуру, что использует встроенная:
конвертировать ничего не нужно. Альтернатива — оставить внешнюю VictoriaMetrics и
указать на неё `DUMBMONIT_VM_URL`.

Что сервер делает сам при первом запуске:

- Переменные `EZYMONIT_*` по-прежнему читаются как запасной вариант, с одним предупреждением
  при запуске на каждую переменную (`EZYMONIT_X is deprecated, use DUMBMONIT_X`).
- `/data/ezymonit.db` переименовывается в `dumbmonit.db`.
- Токены агентов `ezym_…` продолжают работать; новые имеют вид `dmon_…`. Агенты продолжают
  отправлять данные; когда будет удобно, заново выполните команду установки на каждой машине — она
  [переносит старую службу на месте](../devices/agent.md#upgrade).
- Имя cookie сеанса изменилось: всем придётся один раз войти заново. Настройка
  темы в браузере сохраняется.

Чего сервер не делает: префикс метрик изменился с `ezymonit_` на
`dumbmonit_` без обратной совместимости. Старые ряды остаются в VictoriaMetrics под
прежним именем и исчезают по истечении срока хранения; графики и встроенные правила начинаются
заново с момента обновления. Пользовательские правила оповещений, в которых упоминаются метрики `ezymonit_…`, нужно
отредактировать.

## Резервное копирование и восстановление {#backup-and-restore}

Один именованный том, `dumbmonit-data`, содержит всё:

| Путь | Содержимое |
|---|---|
| `dumbmonit.db` | Устройства, правила, каналы, состояние оповещений, сеансы. |
| `secret.key` | Секрет экземпляра. |
| `backups/` | Плановые локальные резервные копии: копия базы данных и секрета, по умолчанию ежедневно, хранится семь. |
| `vm/` | Временные ряды VictoriaMetrics (по умолчанию срок хранения 12 месяцев). |

DumbMonit по расписанию сам резервирует свою базу данных и экспортирует всю
конфигурацию — устройства, учётные данные, правила, каналы — в один файл,
зашифрованный выбранной вами парольной фразой, который восстанавливается на свежий экземпляр.
Оба способа описаны в разделе **[Резервное копирование и восстановление](backup.md)**, вместе с тем, что делать перед
обновлением, и единственным правилом о `secret.key`, которое стоит прочитать дважды.

Чтобы заархивировать сам том, вместе с графиками, остановите стек и упакуйте его в tar:

```bash
docker compose stop
docker run --rm -v dumbmonit-data:/data -v "$PWD:/backup" alpine \
  tar czf /backup/dumbmonit-data.tgz -C /data .
docker compose start
```

Чтобы восстановить, создайте том, распакуйте в него архив таким же образом, затем
выполните `docker compose up -d`.

Если важен объём, `--exclude=./vm` делает архив небольшим: база данных и
секрет — это настройка, а `vm/` — только графики.

## Смена порта {#changing-the-port}

Задайте `DUMBMONIT_PORT` при запуске:

```bash
DUMBMONIT_PORT=8099 docker compose up -d
```

Или поместите `DUMBMONIT_PORT=8099` в файл `.env` рядом с файлом Compose.

## Обратный прокси {#reverse-proxy}

UI и API обслуживаются на одном порту по обычному HTTP. WebSocket не используется:
интерфейс опрашивает API, поэтому любой обратный прокси работает без особой
настройки.

=== "Caddy"

    ```
    monit.example.com {
        reverse_proxy 127.0.0.1:8080
    }
    ```

=== "nginx"

    ```nginx
    server {
        listen 443 ssl;
        server_name monit.example.com;
        # ssl_certificate / ssl_certificate_key …

        location / {
            proxy_pass http://127.0.0.1:8080;
            proxy_set_header Host $host;
            proxy_set_header X-Forwarded-Proto $scheme;
            # После сбоя агенты отправляют накопившиеся пакеты:
            client_max_body_size 16m;
        }
    }
    ```

Если прокси терминирует TLS, задайте `DUMBMONIT_COOKIE_SECURE: "1"`, чтобы cookie сеанса
отправлялась только по HTTPS. Не задавайте её при развёртывании по обычному HTTP: браузер
никогда не вернёт cookie, и войти будет невозможно.

!!! note "Агенты за прокси"
    Команда установки, показываемая при создании токена агента, использует URL, по которому
    ваш браузер открыл UI. Если это URL прокси, агенты будут использовать
    его тоже: убедитесь, что `/install.sh`, `/install.ps1`, `/download/…` и `/api/ingest`
    проходят через прокси.

## Работа от имени обычного пользователя {#runs-as-a-non-root-user}

Контейнер запускает сервер от пользователя `65532:65532` (числовой: в образе `scratch`
нет `/etc/passwd`), со всеми отброшенными capabilities, `no-new-privileges`
и корневой файловой системой только для чтения; `/data` (том) и `/tmp` (tmpfs)
— единственные доступные для записи пути. Всё это есть в файле Compose выше.

Именованный том, созданный Docker при первом запуске, наследует владельца `/data`
из образа: делать ничего не нужно. Два случая требуют одной команды:

- **Том, созданный более ранней версией** (сервер раньше работал от root,
  поэтому файлы принадлежат root). Передайте их один раз, с остановленным стеком:

  ```bash
  docker compose stop
  docker run --rm -v dumbmonit-data:/data alpine chown -R 65532:65532 /data
  docker compose up -d
  ```

  Иначе симптом — контейнер, который сразу завершается с
  `creating directory /data … Permission denied` (или `unable to open database
  file`).

- **Привязанный каталог** (`./data:/data`) сохраняет владельца каталога хоста.
  Либо `chown -R 65532:65532 ./data`, либо запустите контейнер от имени владельца
  каталога: `user: "1000:1000"` в сервисе, подойдёт любой uid.

## Ping ICMP без capability {#icmp-ping-without-a-capability}

[Монитор ping](../devices/services.md#ping) отправляет ICMP-эхо. Вместо
сырого сокета — которому нужна `NET_RAW`, а capability, выданная непривилегированному
пользователю контейнера, всё равно непригодна, — он использует сокет ICMP echo, который Linux
разрешает группам, перечисленным в `net.ipv4.ping_group_range`. Файл Compose
задаёт этот sysctl внутри собственного сетевого пространства имён контейнера:

```yaml
    sysctls:
      net.ipv4.ping_group_range: "0 2147483647"
```

На хосте ничего не меняется. Docker 20.10 и новее сами задают этот диапазон в каждом
контейнере; явные строки обеспечивают его на более старых версиях и
в Podman. Без него проверка сообщает об ошибке конфигурации (показывается на
устройстве, без уведомления), но не о ложном «хост недоступен». При использовании `docker run` передайте
`--sysctl net.ipv4.ping_group_range="0 2147483647"`.

## Проверка без оборудования {#testing-without-hardware}

Добавьте [демо-устройство](../devices/demo.md): оно генерирует поддельные измерения без
какой-либо подготовки, так что графики, правила и уведомления можно опробовать
сразу. Для реальных данных SNMP часто достаточно машины, на которой запущен Docker, —
установите на ней `snmpd` (`apt install snmpd`, разрешите сообщество `public` в мосте Docker
в `/etc/snmp/snmpd.conf`) и добавьте устройство SNMP с адресом
хоста в этом мосту (по умолчанию `172.17.0.1`): профиль определится
автоматически, и появятся интерфейсы, память и процессы.

Разработчики могут добавить оверлей `docker-compose.dev.yml`, чтобы опубликовать встроенную
VictoriaMetrics на `:8428` хоста для прямых запросов MetricsQL:

```bash
docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d
```
